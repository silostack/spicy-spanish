# Schedule / Lesson Data Remediation (timezone + duplicates)

**Audience:** an engineer or agent with shell + `psql` access to the **production database**.
**Goal:** understand why course schedules and lessons show wrong times / duplicates / missing days, and fix the data safely.

This document is self-contained. Read the **Critical prerequisite** first — fixing the data is pointless if the cause is still running.

---

## TL;DR

1. Lessons were generated by an **old build of the backend** running on a **UTC+2 server**. Course schedule times are bare wall-clock strings (e.g. `"17:00"`) with **no timezone**; the old code interpreted them in the server's local zone, so every lesson was stored at the wrong absolute instant (≈7h off for a Bogotá school).
2. The school's real timezone is **`America/Bogota` (UTC−5, no DST)**. The fixed backend anchors schedule times to this zone via `date-fns-tz` and is independent of server time.
3. Repeated generation runs (and one duplicate `course_schedule` row) also produced **duplicate lessons**.
4. **Critical:** if production is still running the OLD backend, its nightly 2 AM cron (`LessonGeneratorService.generateLessons`) will **re-create wrong-time lessons after every cleanup**. You must confirm the new code is live *before* cleaning data, or the fix will be undone within a day.

The remediation SQL is at **`backend/scripts/remediate-schedule-data.sql`**.

---

## Symptoms

- Lesson times are shifted by a fixed offset (the gap between the server zone and Bogotá). Example seen in prod: a "12:00" class displayed as **05:00** to a viewer at UTC−5, because it was stored at **10:00 UTC** (`12:00` interpreted on a UTC+2 server = `10:00 UTC`; `10:00 UTC` shown at −05 = `05:00`).
- The same class appears **multiple times on one day** (duplicate lessons at the same instant).
- Some scheduled days **don't show up**, or upcoming lessons are missing.
- Days listed **out of order** (this part is purely a frontend sort bug, fixed in the app — not a data problem).

### The timezone math (how to read stored values)

Schedule times are the intended **Bogotá wall-clock**. The correct stored instant is that time at `America/Bogota`:

| Schedule (Bogotá wall) | Correct stored UTC | What a UTC−5 viewer should see |
|---|---|---|
| 12:00 | 17:00 UTC | 12:00 |
| 17:00 | 22:00 UTC | 17:00 |
| 16:00 | 21:00 UTC | 16:00 |

If a class is stored at **10:00 UTC** for a "12:00" schedule, that is the **old UTC+2 bug** (`12:00 − 2h = 10:00 UTC`), not the correct value.

## CRITICAL PREREQUISITE: is the fixed code actually running?

The data cannot stay fixed while the old backend is live. Confirm **before** touching data.

**Why it matters:** The new `LessonGeneratorService` computes instants with `zonedTimeToUtc(\`${date}T${slot.startTime}:00\`, 'America/Bogota')` — it does **not** use server time. The old build used `new Date()` + `setHours()` in the server's local zone. So:

- If you ever see lesson instants whose offset matches the **server's** timezone rather than Bogotá, the **old** code is generating them.
- The old 2 AM cron regenerates for all active courses nightly, so it will refill wrong-time/duplicate lessons after any cleanup.

**How to confirm the new code is live:**

1. **Generator behavior (authoritative):** after the new code runs, every generated lesson for a `"12:00"` slot is at `17:00 UTC`. Check a freshly-generated future lesson:
   ```sql
   SELECT c.title,
          l.start_time AT TIME ZONE 'UTC'           AS stored_utc,
          to_char(l.start_time AT TIME ZONE 'America/Bogota','Dy HH24:MI') AS bogota
   FROM lesson l JOIN course c ON c.id = l.course_id
   WHERE l.start_time > now() AND l.status = 'scheduled'
   ORDER BY l.start_time LIMIT 10;
   ```
   `bogota` must equal the course's schedule wall-clock time. If it's off by the server-zone offset, old code is still generating.

2. **Frontend check:** on the courses page, a multi-day course should list days in order (Mon→Fri). If Friday still appears first, the old frontend is also still deployed.

**Deployment notes for this app:**
- The backend container runs `CMD ["node", "dist/main"]` — it does **not** run migrations on boot, so an out-of-sync migrations table does **not** block startup.
- Pushing to `main` runs CI (lint/test/build) only; there is **no CD** in the repo. A deploy/restart must be triggered manually or by the hosting platform.
- The new code needs the `lesson.original_start_time` column to exist (see Schema reference). The remediation script adds it idempotently; the app does not.
- The school zone is configurable via env `SCHEDULE_TIMEZONE`, default `America/Bogota`. Setting it is optional.

**Do not proceed to data cleanup until generated lessons land at Bogotá times.**

## Diagnostics (read-only)

Connect: `psql "$DATABASE_URL"` (or the prod connection string).

```sql
-- Overall counts
SELECT 'total_lessons' k, count(*)::text v FROM lesson
UNION ALL SELECT 'future_scheduled', count(*)::text FROM lesson WHERE start_time>now() AND status='scheduled'
UNION ALL SELECT 'past_scheduled',   count(*)::text FROM lesson WHERE start_time<=now() AND status='scheduled'
UNION ALL SELECT 'completed',        count(*)::text FROM lesson WHERE status='completed'
UNION ALL SELECT 'dup_schedule_rows', count(*)::text FROM (
  SELECT 1 FROM course_schedule GROUP BY course_id,day_of_week,start_time,end_time HAVING count(*)>1) d
UNION ALL SELECT 'lesson_dupe_groups', count(*)::text FROM (
  SELECT 1 FROM lesson GROUP BY course_id,start_time HAVING count(*)>1) d;

-- What Bogota wall-clock times do lessons actually sit at, per course?
-- (Compare against course_schedule; any mismatch = wrong-time data.)
SELECT c.title,
       to_char(l.start_time AT TIME ZONE 'America/Bogota','Dy HH24:MI') AS bogota,
       l.status, count(*)
FROM lesson l JOIN course c ON c.id=l.course_id
GROUP BY c.title, bogota, l.status
ORDER BY c.title, min(l.start_time);

-- The intended schedule for reference
SELECT c.title, cs.day_of_week, cs.start_time, cs.end_time
FROM course_schedule cs JOIN course c ON c.id=cs.course_id
ORDER BY c.title, cs.day_of_week, cs.start_time;

-- Duplicate lessons, and whether they carry attendance/reports (protected)
SELECT c.title, l.start_time AT TIME ZONE 'America/Bogota' AS bogota, count(*),
       bool_or(EXISTS(SELECT 1 FROM attendance a WHERE a.lesson_id=l.id)
            OR EXISTS(SELECT 1 FROM class_report r WHERE r.lesson_id=l.id)) AS any_attended
FROM lesson l JOIN course c ON c.id=l.course_id
GROUP BY c.title, l.start_time HAVING count(*)>1
ORDER BY c.title, l.start_time;
```

`day_of_week` is **0=Sunday … 6=Saturday** (JS `getDay()`), matching Postgres `extract(dow from ...)`.

## Remediation script

File: **`backend/scripts/remediate-schedule-data.sql`**. It is **idempotent** and runs inside one transaction. Steps:

1. `ALTER TABLE lesson ADD COLUMN IF NOT EXISTS original_start_time timestamptz(0)` — matches `Migration20260603012400`.
2. Delete duplicate `course_schedule` rows (keep the oldest per course/day/time).
3. **Fix lesson times in place** to the correct `America/Bogota` instant, matched by the lesson's Bogotá day-of-week → its schedule slot. Preserves lesson ids, attendance, reports, reschedules, and Google Calendar links.
4. De-duplicate lessons sharing `(course_id, start_time)`, keeping the best row (completed > attended/reported > scheduled). **Never deletes a row carrying attendance or a class report** (also enforced by FK — see Schema reference).
5. Regenerate **missing** future scheduled lessons for active courses over the next 28 days, anchored to Bogotá, attaching the course's students.

It assumes **at most one schedule slot per (course, day_of_week)** — true after step 2. Lessons whose day-of-week matches no current slot (orphans from a removed slot) keep their old time and are reported in the verification block.

### How to run it safely

1. **Dry run first** — execute it, then `ROLLBACK`, and inspect the verification output:
   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 <<'SQL'
   \i backend/scripts/remediate-schedule-data.sql
   ROLLBACK;
   SQL
   ```
   The script prints, at the end: `dup_schedule_rows` (expect 0), `future_scheduled_lessons` (expect >0), `lesson_dupe_groups` (expect only attended pairs), `lessons_not_matching_any_slot` (orphans), and a per-course Bogotá-time breakdown. Confirm every course's times match its schedule.

2. **Apply** — re-run and `COMMIT` (the file ends with a commented `COMMIT;`; either uncomment it, or run the file then issue `COMMIT;`):
   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 <<'SQL'
   \i backend/scripts/remediate-schedule-data.sql
   COMMIT;
   SQL
   ```

3. Re-run the **Diagnostics** queries to confirm the persisted state.

> If the old backend is still live, run this **only after** deploying the new code. Otherwise the 2 AM cron will reintroduce wrong-time lessons.

## Verification (expected after a correct run)

- `dup_schedule_rows` = **0**
- `future_scheduled_lessons` > 0 (≈ 28-day window across active courses' slots)
- Per-course Bogotá times exactly match `course_schedule` (e.g. Cameron 17:00, Chris G 12:00 + Wed 08:30, John Casto 16:00)
- `lessons_not_matching_any_slot` = **0** (or a small known set you accept)
- Attendance/report counts unchanged (history preserved)

## Known manual item

Duplicate lessons where **both** rows carry attendance **and** a class report cannot be auto-resolved (deleting either discards real history and may affect the package hours balance). The script leaves them. Find them with the duplicate-lessons diagnostic above (`any_attended = true`) and reconcile by hand — decide which to keep and whether an hour was double-counted.

## Migration baseline (separate cleanup)

The prod `mikro_orm_migrations` table may be **empty** even though the schema exists (the DB was built via `setup-db.sh` / `schema:update`, not migrations). Consequences:

- `npm run migration:up` will try to recreate existing tables and **fail**. It is currently unusable on prod.
- This does **not** block the app (no migrate-on-boot) and does **not** block the remediation script (it adds the column directly).

To repair later (optional, not required for this fix): insert the already-applied migration names into `mikro_orm_migrations` so only genuinely new migrations run. Verify with `npm run migration:pending` — if it lists migrations whose tables clearly already exist, the table needs baselining.

## Schema reference

**`course_schedule`** — recurring weekly slots:
- `day_of_week` int, **0=Sun … 6=Sat**
- `start_time`, `end_time` — **`"HH:MM"` strings**, wall-clock in the school zone, **no timezone**

**`lesson`** — concrete occurrences (`timestamptz`):
- `start_time`, `end_time` — absolute instants (`timestamp with time zone`)
- `status` — `scheduled | completed | cancelled | no_show`
- `original_start_time` (nullable) — set on the **first** manual reschedule to the original generated instant; `NULL` = purely auto-generated. Used to preserve reschedules and prevent the generator recreating a moved occurrence.
- `tutor_id`, `course_id`

**Foreign keys referencing `lesson`:**
- `lesson_students.lesson_id` → **ON DELETE CASCADE** (pivot rows auto-clean)
- `attendance.lesson_id` → **NO ACTION** (an attended lesson **cannot** be deleted — DB errors)
- `class_report.lesson_id` → **NO ACTION** (same protection)

**Pivots:** `lesson_students(lesson_id, user_id)`, `course_students(course_id, user_id)`.

**Relevant code (fixed build):**
- `backend/src/scheduling/schedule-timezone.ts` — `SCHEDULE_TIMEZONE` (default `America/Bogota`)
- `backend/src/scheduling/lesson-generator.service.ts` — Bogotá-anchored generation, 28-day window, dedupe on `start_time` OR `original_start_time`
- `backend/src/courses/courses.service.ts` — `resyncFutureLessons` regenerates on schedule add/remove, preserving reschedules
- `backend/src/migrations/Migration20260603012400.ts` — adds `original_start_time`
